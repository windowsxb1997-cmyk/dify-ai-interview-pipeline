# 手搓教程：单场访谈分析工作流（环节 4）

> 目标：不看 DSL 文件，从零在 Dify 1.17.0 界面里徒手搭建出完整工作流。
> 适用场景：面试现场演示 / 深入理解每个节点。
> 预计耗时：熟练后 20~30 分钟。

---

## 0. 全局蓝图（先背下来这张图）

```
开始（文件+受访者编号+关键词）
   │
   ▼
文字稿提取（文档提取器）
   │
   ├──────► 高频词统计（代码节点）
   ├──────► ① 用户画像提取（LLM）
   ├──────► ② 关键词情感分析（LLM）
   └──────► ③ 判断信号与归类（LLM）
   │
   ▼
结束（5 个输出字段）
```

**一句话讲解词**：输入一份英文访谈逐字稿和研究员关注的关键词，四个分析模块并行跑，输出高频词统计、结构化用户画像、关键词情感分析、信号判断与用户归类，LLM 节点同时输出 JSON 供后续多场汇总。

---

## 1. 开始前准备（30 秒检查）

- [ ] 模型供应商已配置：通义千问（Tongyi），可用模型如 `qwen-max`
- [ ] 手边有测试文件：一份英文访谈逐字稿 `.txt` 或 `.docx`
- [ ] 知道入口：工作室 → 「创建空白应用」→ 选「**工作流**」类型

---

## 2. 创建应用

1. 工作室 → 右上角「**创建空白应用**」
2. 选择「**工作流**」（不是聊天助手、不是 Agent）
3. 名称：`单场访谈分析-头戴耳机健身场景`，图标随意
4. 进入编排画布，默认已有一个「开始」节点

---

## 3. 节点 1：开始节点（3 个输入变量）

点击「开始」节点，在右侧「输入字段」区域点「**+ 添加字段**」，添加 3 个：

| 字段名（variable） | 显示名称 | 类型 | 必填 | 关键配置 |
|---|---|---|---|---|
| `interview_file` | 访谈文字稿 | **文件** | 是 | 允许的文件类型：勾选「**文档**」（覆盖 docx/txt/md/pdf） |
| `interviewee_name` | 受访者编号/姓名 | 文本 | 是 | 默认即可 |
| `keywords` | 研究员关注关键词 | **段落** | 是 | 提示语填：`每行一个或用逗号分隔，例如：noise cancelling, heat` |

> ⚠️ 坑点 1：文件类型变量的「允许文件类型」必须勾选文档类，否则后面文档提取器拿不到内容。
> 🎤 讲解词：段落类型支持多行长文本，适合研究员一次输入多个关键词；文件上传让逐字稿不用复制粘贴。

---

## 4. 节点 2：文字稿提取（文档提取器）

1. 从开始节点右侧拉出一条线，松手后选「**文档提取器**」（Document Extractor）
2. 配置：**输入变量** → 选择 `开始 / interview_file`
3. 输出变量自动生成：`text`（提取出的纯文本字符串）

> 🎤 讲解词：docx/pdf 是二进制，LLM 读不了，这个节点负责把文件变成纯文本。

---

## 5. 节点 3：高频词统计（代码节点）

1. 从「文字稿提取」拉线 → 选「**代码执行**」
2. 标题改为：`高频词统计`
3. **输入变量**：点「+ 添加」，变量名填 `text`，来源选 `文字稿提取 / text`
   > ⚠️ 坑点 2（最容易翻车）：代码节点的输入**必须在这里逐个添加变量**，变量名要和代码里 `main()` 函数的参数名**完全一致**。少加或名字写错，运行时函数拿不到值。
4. 语言选 **Python3**，粘贴代码：

```python
import re
from collections import Counter

STOPWORDS = set("""a an the and or but if then else when while at by for with without about into through during before after above below to from up down in out on off over under again further once here there all any both each few more most other some such no nor not only own same so than too very can will just don should now i me my we our you your he him his she her it its they them their this that these those am is are was were be been being have has had having do does did doing would could ought im youre hes shes its weve theyre ive youve weve ill youll well oh ah wow hey hi hello thank thanks please uh um umm hmm mhm yeah yep yup nope okay ok alright like know think thought really actually basically literally get got go going went want need make take see look thing things stuff lot lots kinda sorta maybe probably sure feel felt say said right""".split())

def main(text: str) -> dict:
    words = re.findall(r"[a-zA-Z][a-zA-Z'-]{2,}", text.lower())
    words = [w.strip("'-") for w in words]
    words = [w for w in words if w and w not in STOPWORDS]
    counter = Counter(words)
    top = counter.most_common(30)
    lines = ["{}. {} —— {} 次".format(i + 1, w, c) for i, (w, c) in enumerate(top)]
    return {
        "top_words": "\n".join(lines) if lines else "（未统计到有效词汇）",
        "total_words": len(words),
        "unique_words": len(counter)
    }
```

5. **输出变量**：点「+ 添加」3 个（名字要和 return 字典的 key 一致）：

| 输出变量 | 类型 |
|---|---|
| `top_words` | String |
| `total_words` | Number |
| `unique_words` | Number |

> 🎤 讲解词：**为什么词频统计不用 LLM 而用代码节点？** 因为计数是精确计算，LLM 会数错而且贵；代码节点免费、毫秒级、100% 准确。同时过滤了英文停用词和访谈口头禅（yeah、like、um），不然 Top 30 全是废话词。
> ⚠️ 坑点 3：Dify 代码沙箱**不能装第三方库**，只能用标准库（re、collections、json、datetime 这些都没问题）。

## 6. 节点 4：① 用户画像提取（LLM 节点）

1. 从「文字稿提取」再拉一条线 → 选「**LLM**」
2. 标题改为：`① 用户画像提取`
3. **模型**：右上角选择 通义千问 → `qwen-max`
4. **参数**：temperature 调为 `0.2`（分析任务要稳定不要发散）
5. **SYSTEM 提示词**（点输入框，直接粘贴）：

```
你是一名资深用户研究员，就职于一家头戴式耳机公司。我们正在研究「在健身房佩戴头戴式耳机（over-ear/on-ear headphones）」的北美用户，重点关注爽点、痛点与换购机会。

你的任务：阅读一场英文用户访谈的逐字稿，严格按照下面的模板输出结构化分析报告。

输出要求：
- 报告正文用中文撰写；引用受访者原话时保留英文原文，并在括号内附中文翻译
- 信息未提及就标注「未提及」，严禁编造或推测
- 每个关键结论尽量附一句英文原话作为证据
- 评分必须给出评分依据

模板：

## 一、基本信息
- 健身房类型（学校 / 公司 / 商业 / 公寓 / 其他）
- 年龄段 / 职业（如提及）
- 健身频率与训练类型

## 二、耳机使用情况
- 大耳罩型号与价格（如提及）
- 过去一个月健身时的佩戴频率
- 最常佩戴的运动场景
- 明确不佩戴的场景

## 三、核心佩戴动机

## 四、降噪/隔噪需求
- 评分（1-7 分）+ 评分依据

## 五、闷热/汗/清洁问题
- 严重程度（1-7 分）+ 具体触发情境

## 六、稳定性/夹持/取戴问题

## 七、设备组合与携带方式

## 八、优先级排序
- 用户最看重的前三项（从以下维度归纳：降噪/隔噪、音质、稳固、轻、夹持舒适、散热、抗汗、清洁、语义、续航、外观、价格、品牌）

## 九、现有替代方案与态度

## 十、换购触发因素

## 十一、一句话洞察
（用一句话概括这个用户最本质的特征与机会点）

最后，在报告之后输出一个 JSON 代码块（```json），供后续多场汇总分析使用，字段如下：
{
  "gym_type": "",
  "age_or_occupation": "",
  "fitness_frequency": "",
  "training_type": "",
  "headphone_model": "",
  "wearing_frequency": "",
  "core_motivation": "",
  "anc_score": null,
  "heat_score": null,
  "top3_priorities": [],
  "repurchase_triggers": "",
  "one_sentence_insight": ""
}
```

6. **USER 提示词**：

```
受访者编号：{{#start.interviewee_name#}}

访谈文字稿：
{{#doc_extract.text#}}
```

> ⚠️ 坑点 4：变量引用不用手打——在提示词输入框里点右上角的 **{x}** 图标（或输入 `/`）从菜单里选「开始 → interviewee_name」和「文字稿提取 → text」。节点名按你画布上显示的名字来，插入后系统会自动处理引用格式。
> 🎤 讲解词：这个模板来自我真实访谈项目的「单用户记录表」；最后让 LLM 额外吐一个 JSON 块，是给下游"多场汇总报告"工作流吃的结构化数据——**Markdown 给人看，JSON 给机器看**。

## 7. 节点 5：② 关键词情感分析（LLM 节点）

从「文字稿提取」拉线 → LLM，标题 `② 关键词情感分析`，模型同上，temperature 0.2。

**SYSTEM：**

```
你是一名资深用户研究员。研究员给出了一组关注关键词，你的任务是：针对每一个关键词，分析英文访谈逐字稿中受访者的相关表述与情感态度。

对每个关键词，严格按以下格式输出（用中文撰写，引用保留英文原文并附中文翻译）：

### 关键词：xxx
- **提及次数**：N 次
- **情感态度**：正面 / 负面 / 混合 / 中性 / 未提及
- **代表性原话**（最多 3 条，英文原文 + 中文翻译）
- **对使用/购买决策的影响程度**：高 / 中 / 低（给出判断依据）
- **小结**：2-3 句中文

分析规则：
1. 同义词和近义表达也算提及。例如关键词是 heat，则 hot、sweaty、stuffy、sweat、ventilation 等相关表述都要纳入
2. 结合上下文判断情感，不要孤立看单个词；受访者语气犹豫或前后矛盾时如实标注「混合」
3. 完全没有提及就如实写「未提及」，不要编造引用
4. 区分「受访者主动提出」和「被研究员问到才回答」，主动提出的权重更高，请在原话后标注（主动提及 / 被问及）
```

**USER：**

```
受访者编号：{{#start.interviewee_name#}}

研究员关注的关键词：
{{#start.keywords#}}

访谈文字稿：
{{#doc_extract.text#}}
```

> 🎤 讲解词：这个节点是研究员视角的"定制放大镜"——每场访谈研究员关注点不同，关键词作为输入参数传进来，同一份工作流就通吃所有研究主题。规则里特意区分"主动提及/被问及"，因为用户研究里主动说出的痛点权重更高。

## 8. 节点 6：③ 判断信号与归类（LLM 节点）

从「文字稿提取」拉线 → LLM，标题 `③ 判断信号与归类`，模型同上，temperature 0.2。

**SYSTEM：**

```
你是一名资深用户研究员，就职于一家头戴式耳机公司。请基于下面的「判断信号框架」，对这场英文访谈做出评估。

对以下 6 个判断问题，逐一给出：判断结论（强信号 / 弱信号 / 信号混合 / 信息不足）+ 依据（引用英文原话 + 中文翻译）：

1. **大耳罩健身是否是稳定行为？**
   - 强信号：每周多次戴；多个运动场景都戴；会主动把耳机带进健身包
   - 弱信号：只是偶尔忘带其他耳机才戴；只做极轻量运动时戴；没有形成习惯
2. **核心价值是否明确？**
   - 强信号：能清楚说出「为什么必须戴大耳罩」（沉浸、降噪、不想塞耳、风格、音质等）
   - 弱信号：只是「手边刚好有」；没有明显偏好；痛点大于收益
3. **闷热/汗是否是高优先级问题？**
   - 强信号：多次提到热、汗、耳垫湿、味道、清洁麻烦；影响下次是否佩戴
   - 弱信号：知道会热但不在意；只在极端运动中出现；愿意忍
4. **降噪是否真需求？**
   - 强信号：主动打开 ANC；健身房噪声影响训练；愿意为更好隔噪付费
   - 弱信号：只是为了让音乐更大声；反而担心听不到周围；从不开 ANC
5. **稳定性是否阻碍高强度运动？**
   - 强信号：跑步/跳跃/卧推等动作明确导致滑动、移位或不安全感
   - 弱信号：主要做器械或低冲击运动，稳定性基本够用
6. **是否存在换购机会？**
   - 强信号：现有产品在健身场景明显不适配，但用户仍坚持戴，说明需求强
   - 弱信号：现有产品已经足够好；只等坏了再换；不愿为健身场景单独购买

然后输出「用户归类」：
- **用户类型**：沉浸训练型 / 风格展示型 / 音质优先型 / 不想塞耳型 / 办公通勤顺带型 / 偶发替代型（可组合，标注主次）
- **健身强度**：低冲击器械 / 力量训练 / 有氧器械 / 跑跳类高冲击 / 团课
- **大耳罩角色**：主力健身耳机 / 通勤办公耳机顺带健身 / 备用耳机 / 只在特定动作使用
- **痛点强度**：无感 / 可忍 / 经常抱怨但继续用 / 已经影响佩戴 / 已经考虑换购
- **机会判断**：已有强需求且现有产品不适配 / 现有产品基本满足 / 行为不稳定 / 只是个别场景

规则：判断必须基于文字稿证据，信息不足就如实标注，不要编造。

最后输出一个 JSON 代码块（```json）：
{
  "stable_behavior": "strong|weak|mixed|unknown",
  "clear_value": "strong|weak|mixed|unknown",
  "heat_priority": "strong|weak|mixed|unknown",
  "anc_real_need": "strong|weak|mixed|unknown",
  "stability_blocker": "strong|weak|mixed|unknown",
  "repurchase_opportunity": "strong|weak|mixed|unknown",
  "user_type": "",
  "fitness_intensity": "",
  "headphone_role": "",
  "pain_severity": "",
  "opportunity_judgment": ""
}
```

**USER：**

```
受访者编号：{{#start.interviewee_name#}}

访谈文字稿：
{{#doc_extract.text#}}
```

> 🎤 讲解词：这个框架是我之前人工访谈时每场结束后必做的判断——现在把它原封不动固化成 prompt，等于把研究员的分析方法论资产化。

## 9. 节点 7：结束节点

1. 从「高频词统计」拉线 → 「**结束**」节点
2. 点击结束节点，「**输出变量**」点 + 添加 5 个：

|---|---|
| `interviewee` | 开始 / interviewee_name |
| `top_words` | 高频词统计 / top_words |
| `profile_report` | ① 用户画像提取 / text |
| `keyword_sentiment` | ② 关键词情感分析 / text |
| `signal_assessment` | ③ 判断信号与归类 / text |

> ⚠️ 坑点 5：结束节点本身不用连线也能输出，但**把 4 个分支都连上结束节点**能保证执行顺序清晰，画布也好看。

## 11. 测试运行

1. 右上角「**预览**」→ 右侧出现运行面板
2. 上传测试逐字稿（txt/docx）
3. 受访者编号填：`US-DU-001`
4. 关键词填：`noise cancelling, heat, clamping force, style, price`
5. 点运行 → 观察每个节点变绿（可点开看每个节点的输入/输出，面试时展示这个追踪过程很加分）
6. 检查 5 个输出字段

> ⚠️ 坑点 6：如果 LLM 节点报模型错误 → 节点右上角重新选一次模型。如果文档提取报错 → 检查文件类型是否在开始节点勾选了「文档」。

## 12. 面试高频追问 & 标准回答

| 面试官可能问 | 回答要点 |
|---|---|
| 为什么 4 个分析节点并行而不是串行？ | 它们彼此无依赖，并行能省 3 倍时间；且职责单一，哪个分析不满意只改哪个 prompt |
| 为什么词频统计用代码节点？ | 计数是精确任务，LLM 不适合且浪费 token；代码节点零成本零误差 |
| 提示词怎么设计的？ | 来自真实访谈方法论：单用户记录表模板、强/弱信号判断框架、用户归类维度；要求"引用原文"是为了防幻觉、可溯源 |
| 怎么控制幻觉？ | 三条：①明确"未提及就标注未提及" ②要求每个结论附原文引用 ③temperature 调到 0.2 |
| JSON 块是干嘛的？ | 下游多场汇总用：单场输出结构化 JSON，N 场跑完后汇总工作流直接聚合统计，不用再解析长文本 |
| 逐字稿太长怎么办？ | 大模型上下文有限，超长可分块（迭代节点）或先让 LLM 做一轮摘要压缩；实际 45 分钟访谈约 8k-12k tokens，qwen-max 放得下 |
| 英文稿子为什么报告用中文？ | 访谈对象是北美用户（英文原声证据），报告读者是国内研究团队（中文结论）——引用保留英文原文方便回溯 |

## 13. 现场手搓时间分配建议（30 分钟版）

| 时间 | 动作 |
|---|---|
| 0-3 min | 创建应用 + 开始节点 3 个变量 |
| 3-5 min | 文档提取器 |
| 5-10 min | 代码节点（粘贴代码 + 配输入输出） |
| 10-22 min | 三个 LLM 节点（提示词提前存在备忘录里直接粘贴） |
| 22-26 min | 结束节点 + 连线 |
| 26-30 min | 运行测试 + 边等边讲解设计思路 |

**应急简化版（只有 15 分钟）**：砍掉节点 ②（情感分析），把它的逻辑并进节点 ① 的 prompt 里；代码节点也砍掉。核心展示"提取 → LLM 分析 → 结构化输出"的主链路即可。

**最重要的一条**：提示词不要现场默写，提前把本教程第 5-8 节的内容存在手机备忘录/剪贴板工具里，现场直接粘贴——面试官看的是你的设计思路，不是打字速度。

## 14. 代码节点：vibe coding 时代的面试应对策略

**结论：代码不用手写默写。** 现代工程实践中让 AI 生成代码是常态，面试官也不期待你默写正则表达式。但要做到「三个能」：

### 能一句话讲清结构（背这句）

> 「这段代码四步：① 正则把所有英文单词抠出来 → ② 过滤停用词和访谈口头禅 → ③ Counter 计数取 Top 30 → ④ 格式化返回。因为 Dify 代码沙箱不能装第三方库，所以全程只用标准库，没用 jieba / nltk。」

### 能现场做小改动（面试官最爱临时加需求，提前练熟）

| 临时要求 | 改哪里 | 难度 |
|---|---|---|
| 改成 Top 50 | `most_common(30)` → `most_common(50)` | ⭐ |
| 把 "gym" 也过滤掉 | 往 STOPWORDS 字符串里加 `gym` | ⭐ |
| 统计词对 bigram（如 noise cancelling） | 加一句 `bigrams = [' '.join(words[i:i+2]) for i in range(len(words)-1)]`，再对 bigrams 计数 | ⭐⭐ |
| 结果输出成 JSON | `import json`，return 里用 `json.dumps(...)` | ⭐⭐ |
| 改成统计中文词频 | 正则换 `[\u4e00-\u9fff]`，改用逐字/简单切分，并说明「正式方案应该用 jieba，但沙箱装不了第三方库」 | ⭐⭐ |

### 必须死记的「接口契约」（这是 Dify 平台规则，不是代码）

1. 入口函数固定是 `main()`，**参数名 = 界面里添加的输入变量名**，对不上就运行报错
2. `return` 字典的 **key = 界面里配置的输出变量名**
3. 沙箱只能用 Python 标准库，**不能 pip install**

这三条记住了，就算代码全忘，现场让 AI 重写一份也能立刻接回工作流——这才是 vibe coding 的正确姿势：你负责架构和接口，AI 负责实现细节。
